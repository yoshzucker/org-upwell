#+title: org-upwell
#+options: toc:2 num:nil

Files rising to the heading that is being lived.

A user heading -- a project, a task, a meeting -- has a *domain*. The bench
lays it out: the Org entry, and the files and URLs that claim it, each with
where it lives. Reading comes before opening, and they are two
acts -- where a thing is and what kind of thing it is are what make it worth
opening at all. Those files are not listed under the heading; they point up
at its id. ~upwell.org~ is storage for those identities, not the work.

Capture happens *outside* Emacs. A resident watcher records the frontmost
document and, when it can, the browser URL, without a hotkey and without
Emacs being focused. Attribution is the intersection of those traces with
CLOCK intervals, including clocks filled in afterwards from the agenda.

It is one of three verticals, and it works with the other two if you have
them, but needs neither: [[https://github.com/yoshzucker/org-foresight][org-foresight]] answers *when* a thing fits on the
day, [[https://github.com/yoshzucker/org-convect][org-convect]] carries purpose down the ladder of horizons and reduces
it back up. This one runs at the day's feet, where the work touches files.

* Install (Emacs)

#+begin_src emacs-lisp
(use-package org-upwell
  :after org
  :config
  (org-upwell-mode 1))
#+end_src

With straight.el, keep the ~script/~ directory -- it is where the watcher
lives:

#+begin_src emacs-lisp
:straight (org-upwell :host github :repo "yoshzucker/org-upwell"
                      :files ("*.el" ("script" "script/*")))
#+end_src

~org-upwell-mode~ registers org-protocol, the clock hooks, drop handlers,
and a quiet sync timer. It does *not* start the watcher: the watcher is a
process of its own.

If your configuration already has a policy for opening files -- which
extensions belong to the OS and which are read inside Emacs -- give it to
~org-upwell-open-function~ rather than have it decided twice:

#+begin_src emacs-lisp
(setq org-upwell-open-function #'your-open-function)
#+end_src

Unset, files go to the OS default application.

* Install (the watcher)

The watcher has to be a login item rather than an Emacs subprocess. On
macOS a privacy prompt raised by a subprocess is attributed to Emacs, which
carries no Automation usage string, so the dialog never appears. On
Windows, a watcher that dies with Emacs stops catching the hour the moment
the frame is closed.

Use the AutoHotkey watcher on Windows and the osascript watcher on macOS.
The PowerShell watcher is a fallback for a machine without AutoHotkey.

** Windows

Once, from the package directory:

: powershell -NoProfile -ExecutionPolicy Bypass -File script\install-startup.ps1

That puts a shortcut in the Startup folder pointing at
~script/org-upwell-watch.ahk~ *in place* -- not a copy -- so updating the
package and logging back in is what picks up a new version. Log off or
restart to start it. Emacs does not have to be running.

** macOS

Once, from the package directory:

: bash script/install-launchagent.macos

That writes ~~/Library/LaunchAgents/org.upwell.watch.plist~ with this
machine's paths and bootstraps the job. Re-run it after moving the package.
The first capture asks for Automation permission -- grant it to this job,
not to Emacs.

For a one-off test session only, and not how it should run day to day:

: M-x org-upwell-watch-start

meant opening its files. It is ~bench~ now -- one noun for the buffer, the
listing and the act of asking for it. The old names are obsolete aliases,
including ~expand=~ in the org-protocol URL.

The bench is half a window wide and truncates rather than wraps, so the
layout falls back to one column, and to shorter wording, rather than off
the edge.

** What a row shows, and what it cannot

A row is columns, and a column is a width. The name is cut from its end and
the directory from its beginning, which are opposite on purpose: a name says
what a thing is in its first word, and a directory says which of two it is in
its last. A host is cut like a name — what tells two of them apart is the
first label, and every one of them ends in the same handful of characters.

The echo area says the line at point in full: the name and where it actually
is, which are the two things the columns had to shorten.
~org-upwell-bench-eldoc~ turns it off.

A row says three things about the thing it names, and it takes all three
to trust it: what it is *called*, *where* it lives, and what *form* it is.
The form is the extension when that can be read -- ~pptx~, ~xlsx~, ~pdf~ --
and a word for the kind when it cannot: a SharePoint short link says which
application opens it and nothing else, so it reads ~slides~, ~sheet~ or
~doc~. A page is ~page~ whatever its extension; an ~.aspx~ in that column
would answer a question nobody asked. A directory is ~dir~.

Opening a document on SharePoint and then downloading it leaves two
things, and they stay two: one is a link somebody else can open and the
other is a file on this machine. The bench puts the download under the
original and marks it ~copy~, which is guessed from the names agreeing.

Names that came from a browser are trimmed before they are stored. A browser
writes its own name on every window it owns, and where the watcher can read
nothing finer than the window — Windows, which has no scripting bridge to ask
the tab — that suffix arrives on every URL alike, several columns of it, the
same on every row. ~org-upwell-title-noise~ is the list; it takes one segment
off the end, because nothing tells a profile somebody named apart from the
last part of a title and a rule that took two would eat real subjects. Edge's
default =Profile N= is listed by name.

~N~ on the bench or the grid finds the rest. A site that prefixes every page
with its own name is not guessable -- it is whatever the intranet in front
of you calls itself -- so the store is asked instead: runs of text that
~org-upwell-tidy-threshold~ names or more share, at either end, offered with
their counts.

One at a time. Taking a run off the names changes the names, so what the
rest of them share is a different question -- and a list chosen in one go
stops being true after its first item. It asks again after each, with the
runs the last one left, and ~RET~ on an empty answer stops. What is offered
is the run itself, with the end it sits at and how many names carry it shown
beside it rather than written into it: a run has spaces in it, and a
candidate with spaces asked for several at a time comes back as a fragment.

A run is as long as the names actually agree, not as long as the first
separator. Cutting at =" - "= found the shortest thing worth calling shared
and stopped looking, and what a store full of one intranet's pages shares is
usually longer -- several words, sometimes most of the name. A run that ends
mid-word is offered like any other and passed over like any other; a run
nobody was shown cannot be. ~org-upwell-tidy-minimum~ is how short a run may
be before it is not worth offering. Offered, not stripped: losing real words is worse than keeping
a few noisy ones.

Nothing is learned and nothing is stored. The candidates are counted afresh
from the store on every call, so there is no model to inspect -- and the two
things worth having instead are both there. It hands back the **rule**: a
regexp for ~org-upwell-title-noise~ that strips the same run from every
future sighting, printed once at the end. And ~C-u N~ puts back the names
the last call changed, for the look at the bench straight afterwards when a
word that was part of the name has gone; past that moment ~R~ fixes the one
name that is wrong.

Both are said after the store is written rather than during. Saving clears
the echo area, so a message from inside the write reaches =*Messages*= and
nowhere anybody is looking -- which is what happened to the rule, announced
once per affix inside the loop where the next iteration erased it.

A URL caught by hand goes through the same strip a sighting does. Identity is
exact, so a title carrying =- Microsoft Edge= that a sighting would have
trimmed makes one document into two rows that never meet.

~org-upwell-follow-mode~ is the switch for whether this package draws by
itself at all: in an Org buffer, and -- where ~org-upwell-agenda-follow~
says so -- in the agenda. Off means off in both.

It draws when the keys stop, not on every one of them:
~org-upwell-follow-delay~ seconds of quiet, 0.2 by default, nil to draw at
once. A draw reads the store and lays out a window, and a held-down ~j~ asks
for one every thirty milliseconds; run as they arrive, the drawing falls
behind the keys and point appears to jump in the buffer being read. A run of
headings passed through costs one draw, for the heading stopped at.

Org's own follow (~F~) is a different thing and stays its own: it opens the
entry's file in another window, this draws the listing and nothing else, and
neither reads the other's switch. Both may be on, and then both happen.
Either way, ~TAB~ in the agenda puts the file in the window above the bench
rather than in the strip.

From a launcher, a hotkey, or anything else that can run a command, to put
whatever is being clocked on the bench:

: emacsclient -e "(org-upwell-bench-clock)"

org-protocol, for a browser (bookmarklet in
~script/org-upwell-bookmarklet.txt~):

: org-protocol://upwell?url=…&title=…
: org-protocol://upwell?bench=ORG-ID

* Where the work is done

A heading can say where its work happens. It is ~:UPWELL_DIR:~ on the
heading, which is inherited -- written on a project, every task under it
answers the same way -- and it is the same property ~org-upwell-create~ puts
a new file in, because those are one fact and not two.

The bench says so in its header, under the title:

#+begin_example
Compare the three quotes  upwell.org
work here  …/Documents/project/acme/  main, from "Move to the new vendor"
#+end_example

In the header rather than among the rows. Every row of the listing is a
stored item and every row command expects one, so a row for a directory
nothing stored would look like the others and answer to half their keys --
and it is not a material anyway. It is a fact about the heading, like the
title it sits under. Where the directory *is* also a row, that row is
marked ~main~ as well: the header says where, the mark says which.

Inherited, the header names the heading it came from. ~org-entry-get~ with
inheritance returns the value and not its source, and a directory nobody set
on this heading is one they cannot account for.

Unmarked, the bench guesses: the directory holding the most of this
heading's files, shown as ~main?~. Free and often right, and it is a count
-- a heading whose downloads have piled up guesses the download directory.

~org-upwell-work-here~ settles it, from wherever you are standing, and then
takes you there. Whichever door it is asked from, the same property is
written on the same heading and dired opens on it:

| on the bench, over a directory row | that row, this bench's heading; nothing asked  |
| in dired                           | the directory shown, and the heading is read   |
| anywhere else                      | that heading, and the directory it already says |

Whichever half is in front of you is the half not worth asking about. Where
the heading says nothing yet, the directory is read and written down: "take
me to the work" cannot answer nothing when nobody has ever said where the
work is. The guess is never what gets written -- a download directory
promoted to a project's home by a keystroke nobody read is exactly the
mistake the guess is there to avoid making permanent.

Setting it and going to it were two keys for a while, and nobody could say
at the moment of pressing one which they wanted: naming a place and standing
in it are the same intention a second apart.

The heading is read from Org's own refile targets rather than from the list
the bench offers: that list is what is in flight, and where the work is
*done* is a fact about a project -- which carries no keyword and often holds
nothing yet, so it is in none of it.

~M~ moves this row's file there. It is the one thing this package does to a
file rather than about it, so it asks first, it says when the destination
was a guess, and it never writes over a name already taken: that is a
different document with the same name, and choosing which of them survives
is not a thing a listing gets to do. The store follows the file.

* The family, as a grid

The bench answers one heading, which is the unit for working and the wrong
one for tidying. Tasks come in families -- the next one is the last one
continued, and it was given the same three files -- and after a few rounds
the same document is on six headings, one of which should never have had
it. A single bench cannot show that, because what is wrong is a relation
between two of them.

~T~ on the bench, or ~M-x org-upwell-matrix~. Rows are things, columns are
headings, a cell is a claim: ~X~ is an answer somebody gave, ~?~ a claim
proposed and not yet answered, and a refusal draws nothing. ~?~ is
*provisional*, the same word the bench uses for it -- one status, one name.
The buffer says so above the grid, and the line under the cursor is
highlighted -- a row of marks two characters apart is the easiest thing in
the world to slip off.

The marks are ASCII, and not because ASCII is prettier. ~×~ and ~·~ are East
Asian Ambiguous: in a CJK locale Emacs counts the first as two columns and
the second as one, and a font may draw either way, so a grid built out of
them is a grid whose columns move depending on whose Emacs is drawing it.

#+begin_example
Move to the new vendor
   1  Move to the new vendor
   2    NEXT Compare the three quotes
   3      NEXT Send the recommendation  (no id)
   4    NEXT File the photos
   5    NEXT Read the vendor manual

  X kept here    ? provisional, nobody has answered
          1 2 3 4 5
  dir       X        files              …/demo
  dir       ?        shared             …/demo/files
  slides    X     ?  Vendor day deck    contoso.sharepoint.com
  pptx      X        kickoff.pptx       …/demo/files
  csv       X        quote-acme.csv     …/demo/files
  txt       X        quote-beta.txt     …/demo/files
  page      ?        Vendor list        contoso.sharepoint.com
  txt       ?        brief.txt          …/demo/files
  pdf             X  vendor manual      example.com
#+end_example

Where the family is rooted depends on how you got there, because the two
cases want different answers. *Stood on* a heading -- point, an agenda row,
the running clock -- roots at its **parent**, so standing on a leaf task
shows the siblings it was continued from; its own subtree would be one
column, which is a list. *Named* from a list -- under a prefix argument, or
because there was no heading to stand on -- roots at the **heading itself**:
what somebody picks out of a list is nearly always a container and they mean
what is under it, and its parent would put every sibling project into the
grid at once.

Neither is final. ~<~ moves the root out to the parent and ~>~ moves it in
to the column under the cursor -- left and right as the list above the grid
is drawn, where a child sits to the right of its parent, so the key that
goes to a child points the way the child sits. (The agenda has ~<~ the other
way round, and no indented tree on screen for a direction to disagree
with.) ~f~ reads another heading. Widening is the direction that matters: a
stray file usually came from a neighbouring project, and that is a relation
between two families, invisible until both of their tasks are columns of one
grid -- the same reason a single bench cannot show what is wrong inside one
family. There is no key for jumping to a sibling family, because ~>~ then
~<~ is that, and ~f~ opens any family outright.

The row reads /what it is/, then /which headings hold it/, then /what it is
called/ and /where it is/. The grid sits against the name rather than past
the path: a mark and the thing it is about have to be read together, and
every column between them is one the eye crosses on every row.

The columns are numbered rather than named. Titles as column headers fit
six or eight of them in eighty columns, cut to four characters each, which
is not a word; numbers fit twenty and lose nothing, because the list above
the grid says the rest -- and the heading the cursor's column is shows there
in bold, as well as in the echo area. Bold rather than a second band of
background: the row already has one, and two bands would be two claims of
the same kind about one cursor.

The buffer opens on a cell, and ~h~ and ~l~ walk along the grid while ~j~
and ~k~ change row and stay in the column. Every command here wants a cell
or a column, so opening anywhere else would leave all of them answering
"not on the grid", which is true and useless.

~m~ marks the row and moves down, ~U~ unmarks them all, and ~D~ forgets what
is marked -- or this row, where nothing is. A grid is read to find the things
that should not be in the store, and they are found several at a time.

~d~ takes a thing off this heading, emptying the cell. ~c~ keeps it here,
which answers a ~?~ and fills an empty cell alike -- both are the same act,
saying this belongs here.

Under the grid comes everything no heading holds at all, drawn as rows with
every cell empty:

#+begin_example
  ── attached to nothing: any column above could take these ─────────────
  page               Vendor list (old)   example.com
  xlsx               見積書_v3.xlsx      …/Downloads
#+end_example

They need no command of their own. Taking a thing off a heading was always
easy here -- the mark is in front of you -- but putting one on meant naming
it from memory in a prompt, and remembering what is not on the screen is the
expensive half. ~c~ on one of those empty cells attaches it, which is the
same key that answers a ~?~, because both are saying it belongs here. ~D~
forgets it, which is what most of them are for: a store is what was seen,
and most of what was seen was not work.

Global rather than of this family, and that is what they are -- a thing
attached to nothing is a thing any column here could take.

~a~ brings in something no heading in the family holds. The grid can only
draw what some column already claims, so the file that belongs on this task
but was filed under last month's is exactly the one missing from the
picture, and no amount of reading will show it; ~a~ is the way in. It offers
everything in the store this heading does not hold -- including things
refused before, because changing your mind is the ordinary case -- and
claims the chosen one as an answer, since somebody chose it.

Three keys, because "go there" is three questions on a grid. ~RET~ opens the
thing. ~TAB~ (~C-i~) goes to /its own heading in the store/, where its name,
how it came to be seen and every claim on it are written -- the record the
row is drawn from, and the only place it can be edited by hand. ~v~ goes to
/the heading this column is/, which is a task in a file of your own. Each
lands in a window that is not the grid, and the grid keeps standing.

~RET~ opens the thing on this row and ~^~ goes to the directory it lives in,
both the way the bench does: the line names a thing, and that is the key for
opening what a line names. A grid says which headings hold a thing and where
it is, and neither settles whether it is the right one; opening it is how
that gets settled, and going to a bench to do it means leaving the question
the grid was opened to ask.

~y~ copies a whole column onto another, which is the move that made this
buffer necessary and the one that makes a mess of it. ~R~ renames a thing
and ~D~ forgets it everywhere; neither touches a file.

A heading with no org-id holds nothing and is marked ~(no id)~ -- this
walks your own file, and minting an id for every heading in a subtree in
order to draw a picture of it would be a write nobody asked for.

* How attribution works

Two clocks, not one.

| What | When | Who |
|---|---|---|
| A *trace* (path/URL + unix time) | every 15s, only if the front document changed -- for a browser, only when the window title says the tab or the page did; also new files in the download directory | the watcher, Emacs need not be running |
| The same, for what Emacs is looking at | when the buffer changes: a dired listing's directory, and a file under ~org-upwell-search-roots~ | Emacs itself (~org-upwell-sight-mode~) |
| A *provisional claim* | Emacs intersects traces with CLOCK intervals: a 60s timer while Emacs is up, immediately on clock-out, immediately after a clock is filled in from the agenda | Emacs |
| A *confirmed claim* | ~c~ on the bench, which clock-out opens for the heading it just closed. An explicit pin or drop is confirmed at once | you |
| A *copy* | ~y~ on the bench, or a column onto another in the grid. Provisional, and what the far heading has already settled is left alone | you |
| A *rejection* | ~d~ or ~r~ on the bench. Written down, because the intersection runs again a minute later and would otherwise propose the same file | you |

Clock-out shows the bench and asks nothing: one spell often touches
several files, and a question that names none of them can only be
answered by saying yes. The claims are already written by then, and the
listing marks them as provisional until ~c~ keeps them.
~org-upwell-review-on-clock-out~ can go back to the older single-line
question, or say nothing at all.

A directory somebody had open is kept, like anything else. It was dropped
once, on the reasoning that the bench lists things to /open/ and the
directory a file came from is already on the file's line. That reasoning
holds only for somebody whose file manager is watched from outside; where
the work is kept is a thing to go to, and ~^~ goes there. Directories are
listed above the files, because sorted in among them the place moves every
time a file is added, and it is the one row you go to over and over.

Emacs is the other blind spot the same change closes. The watcher's
branches are the applications work arrives in -- a browser, Excel,
PowerPoint, Word, the file manager -- and Emacs is in none of them, so
while Emacs was in front nothing was recorded at all. ~org-upwell-sight-mode~
writes what Emacs is looking at into the same log: a dired listing's
directory, and a file under ~org-upwell-search-roots~. That setting already
meant "the trees my work lives in"; outside them is a configuration file, a
library, or this package's own store, and none of those is work.
~org-upwell-sight-dired~ and ~org-upwell-sight-files~ turn each half off.

The watcher does not know Org. If Emacs is closed, traces pile up and wait.
Nothing is guessed when there is no clock: that file becomes an unclaimed
item, a row to deal with later, not a wrong project.

An answer you gave -- kept or rejected -- is never overwritten by a later
sample. A rejected file is not on the heading and is unclaimed again; it
just is not offered for that heading a second time.

* Where the files live

| What | Where | Why |
|---|---|---|
| Identity (~upwell.org~) | ~org-upwell-directory~, or ~org-directory~ | it is Org, next to the rest of your Org files |
| Traces (JSONL) | ~org-upwell-trace-directory~, or ~$XDG_DATA_HOME/org-upwell/~ | the watcher is not Emacs; this path has to exist without ~.emacs.d~ |

~.emacs.d~ is for files Emacs writes. The watcher starts at login, often
before Emacs, and must not depend on it.

~org-upwell-search-roots~ answers two questions, and they are the same
question: where a moved file is looked for again, and which of the files
Emacs opens are work. Where ~org-upwell-create~ puts a new one is
~org-upwell-create-directory~ -- or the ~:UPWELL_DIR:~ property on the
heading, when it has one.

* What this is not

- Not org-attach. A screenshot belongs to the note it illustrates; a
  spreadsheet belongs to the application that opens it.
- Not a 1:1 heading-to-directory map. A directory is one appearance of an item,
  not its identity, and one file can belong to two headings.
- Not a document archive. A scanned pile on disk stays on disk until
  something claims it.
- Not a file launcher. Opening a file you can already name is what a
  launcher is for. This answers the other question: which files belong to
  the heading you are living.
